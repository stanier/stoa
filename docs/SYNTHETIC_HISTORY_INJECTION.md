# Synthetic History Injection in LLM Agentic Systems

## What This Is

In this codebase, sub-agent results are delivered back to the parent agent by injecting synthetic
`tool_use` + `tool_result` message pairs directly into the conversation history — pairs that the
LLM never actually generated. The client owns the message array and inserts these on behalf of
the system before the next LLM call.

This is a deliberate design choice. It avoids role ambiguity (vs. injecting as a `user` message),
keeps tool call semantics coherent, and prevents the LLM from confusing machine-generated content
with human input or from being manipulated by adversarial sub-agent output arriving in the `user`
role.

This document records why this technique is valid today and what conditions would have to change
for it to become problematic.

---

## Current API Landscape

### Primary Chat/Completion APIs: Fully Stateless

All major providers expose a core stateless inference API. The client sends the full message
history on every call. The server processes it and returns a response with no memory of prior
calls.

| Provider | API | Stateless? | Server-Side History? |
|---|---|---|---|
| Anthropic | Messages API (`POST /v1/messages`) | Yes | None |
| OpenAI | Chat Completions (`POST /v1/chat/completions`) | Yes | None |
| Google | Gemini `generateContent` | Yes | None |

Under this model, the provider has no knowledge of what the client claimed was generated in prior
turns. There is no session, no thread ID, no record to validate against. The client is the sole
authority over what history gets sent. History injection works trivially because there is nothing
to inject against.

Sources:
- [Anthropic Messages API](https://docs.anthropic.com/en/api/messages): "You always send the full conversational history to the API."
- [Gemini Developer Forum](https://discuss.ai.google.dev/t/stateless-gemini-api-and-maintaining-continuous-conversations-for-multiple-users/41909): "The Gemini API is stateless, so the model treats every API request independently."
- OpenAI Chat Completions has been stateless since launch and this has not changed.

### The Hybrid Shift (2025)

All three major providers launched server-side history management in 2025, as a convenience
abstraction:

- **OpenAI Responses API** (March 2025, now the primary API): `store: true` by default.
  Responses are stored server-side for 30 days. A `previous_response_id` can replace resending
  full history. The deprecated Assistants API used a similar Thread/Run model. [Source](https://platform.openai.com/docs/guides/conversation-state)

- **Google Interactions API** (December 2025, public beta): `previous_interaction_id` replaces
  full history resend. Server retains 55 days (paid tier), 1 day (free). [Source](https://ai.google.dev/gemini-api/docs/interactions)

- **Amazon Bedrock Session Management APIs** (February 2025, preview): Platform-layer session
  storage on top of underlying stateless model APIs. [Source](https://aws.amazon.com/blogs/machine-learning/amazon-bedrock-launches-session-management-apis-for-generative-ai-applications-preview/)

**Important nuance**: when `previous_response_id` or equivalent is used, the server owns the
history and the client cannot inject into it. History injection only works in stateless mode (full
history resend), which remains available at all three providers. It does not require workarounds —
it is a supported mode with no sign of deprecation.

### Reasoning Block Signatures: A Precedent Worth Watching

All three providers have introduced cryptographic tokens scoped specifically to model reasoning
output:

- **Anthropic**: `thinking` blocks carry an opaque `signature` field. If echoed back in a
  subsequent turn, the API validates this signature to confirm the thinking block was genuinely
  generated by Claude. Fake or modified thinking blocks are rejected. [Source](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking)

- **OpenAI Responses API**: `reasoning.encrypted_content` provides encrypted reasoning tokens
  for Zero Data Retention configurations. The API decrypts them in-memory; clients cannot
  fabricate valid tokens. [Source](https://platform.openai.com/docs/guides/reasoning/)

- **Google Gemini**: `thoughtSignature` fields on thinking content blocks. For Gemini 3 models
  during function calling, passing back valid thought signatures is **mandatory** — omitting them
  produces a 4xx validation error. [Source](https://ai.google.dev/gemini-api/docs/thought-signatures)

These mechanisms exist to prevent injection of fabricated reasoning into subsequent turns. They
are currently scoped to reasoning/thinking blocks only. **Ordinary `user` and `assistant`
message turns carry no cryptographic validation at any provider.**

Critically, `tool_use` and `tool_result` blocks are a separate content type from thinking blocks
and are not covered by any of these signature schemes. Gemini 3's mandatory thought signatures,
for example, enforce that the model's *reasoning* is authentic when echoed back — not that its
*function call invocations* are. A synthetic assistant turn containing only a `tool_use` block
(no `thinking` block) has no signature requirement at any provider and can be freely constructed.
The practical edge case on Gemini 3 is if a real assistant turn contained both a `thinking` block
and a `tool_use` block: a subsequent synthetic turn that mimics the same structure would need to
fabricate a `thinking` block too, and a valid signature for it cannot be produced. The solution
is straightforward — synthetic injection turns should not include thinking blocks, and in practice
they don't need to: injecting an agent completion event has no reason to carry reasoning content.

## The Risk Scenario

The reasoning signature pattern is a genuine precedent. The same logic — "the client might inject
fabricated content of type X, so we sign type X" — could eventually be applied to assistant
message turns generally, or specifically to `tool_use` blocks.

If a provider were to:

1. Sign all assistant `tool_use` output at generation time
2. Validate those signatures when the same content is echoed back in subsequent turns

...then injecting synthetic `tool_use` blocks would fail validation, breaking this pattern.

What would motivate this? Likely a security narrative: "users could inject fake tool calls to
manipulate model behavior." This is real, but it conflates injection by a malicious third party
(a genuine threat) with injection by the developer who owns the application (not a threat to the
provider). The distinction rarely survives a press cycle.

### Why This Would Be Counterproductive

The entire agent tooling ecosystem relies on developer control over message history. History
injection is not a niche workaround — it is load-bearing infrastructure for:

- **Conversation compaction and summarization**: replacing old turns with summaries requires
  re-authoring assistant messages
- **Memory systems** (Letta/MemGPT and similar): injecting retrieved memories as prior context
- **RAG**: inserting retrieved documents into historical positions in the conversation
- **Async agent result delivery**: this codebase's specific use case
- **Multi-agent orchestration generally**: every major framework (LangChain, AutoGen, CrewAI,
  Semantic Kernel) manipulates history
- **Prompt caching optimization**: restructuring message order to maximize cache hits
- **Debugging and replay**: re-running conversations from a specific state

Making this stateful and validated would require providers to maintain per-session assistant
output records, validate every assistant message echoed back, and reject any that don't match.
This is architecturally expensive, breaks every one of the above use cases, and would devastate
adoption among the enterprise customers building exactly the pipelines providers are competing to
capture.

### The More Likely Path

If providers move further toward sign/validate, it will probably stay scoped to reasoning content:
reasoning tokens are high-value, are explicitly designed to be echoed, and fabricating them is the
one concrete manipulation vector (feeding the model fake reasoning to influence its conclusions).
General tool_use and assistant message turns are less obviously a target because the developer
already has full control over tool execution — the injection attack surface is mostly already
owned by the developer.

The more likely friction point is the server-managed history APIs (Responses API, Interactions
API) becoming the default path over time, with stateless full-resend mode becoming a secondary
or explicitly "advanced" option. That would not break history injection — it would just require
opting into stateless mode — but it would increase friction for new developers who never learn
that the stateless model exists.
